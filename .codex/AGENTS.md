# Codex Configuration

## コア

- 日本語で回答する
- 調査・確認・説明・レビューではファイルを変更しない
- ファイルの変更は、修正や対応などを明示的に依頼された場合のみ行う
- 結果を大きく左右する選択肢がある場合、または破壊的・外部的な操作が必要な場合のみ、行動前に確認する
- 変更がコミット可能な粒度になったら、コミットするか確認し、承認を得るまではコミットしない
- ユーザー向けに提示するシェルコマンドは fish 互換にする

## ワークフロー

- 探索・計画・実装・検証・報告のアプローチに従う：理解 → 計画 → 実装 → 検証 → 報告
- 変更を加える前に、必ず既存のコードを読んで理解する
- 単純な変更では、既存実装を確認して簡潔な計画を立てたうえで実装する
- 以下のいずれかに該当する場合は複雑な実装として扱い、実装前に詳細な計画を提示する
  1. 複数の層やモジュールを変更する
  2. DB スキーマの変更やデータ移行を伴う
  3. API や既存の互換性に影響する
  4. 認証、権限、課金など高リスク領域を変更する
  5. 複数の設計案があり、選択によって結果が大きく変わる
- 結果を大きく左右する設計判断がある場合は、承認を得てから実装する
- ファイルを変更する前に、現在のブランチと作業ツリーを確認する
- `main`、`develop`、`topic/*` 上ではファイルを変更せず、`feature/<機能名>` や `fix/<修正内容>` などの作業ブランチを作成する
- 未コミットの変更がある場合は、勝手にブランチを作成・切り替えず確認する
- 調査やレビューなど、ファイルを変更しない作業ではブランチを作成しない
- Git リポジトリ外のファイルを変更する場合は、作業ブランチを作成しない

## コーディング原則

- YAGNI、DRY、KISS を守り、特にシンプルさを優先する

### コメント規約

- コメントは最小限にし、明白な処理はコードで意図を表現する
- コメントでは「なぜ」を説明し、回避策や一時的な対処には理由を明記する

## 検証方針

- 変更による影響範囲を確認し、既存の期待値どおりに動作することを検証する
- 変更後は、影響範囲に対応する最小限のテスト、lint、型チェックを実行する
- 実行できない検証がある場合は、理由と未検証の範囲を報告する
- 具体的な検証コマンドは、各リポジトリで定められた開発者向けドキュメントに従う
- DBのデータ確認は、権限的にあなたは行えないので、確認用SQLを生成し、ユーザーに委ねて。

## ツールとリソースの最適化

- 互いに依存しないツール操作は並列で実行する
- 作業開始時に、まず依頼内容を「実装」「一次確認」「仕様調査」「レビュー」のどれに当たるか判定する
- 独立した作業へ明確に分割でき、品質または速度の向上が見込める場合のみ、利用可能なサブエージェントを使用する
  - 作業を分担できる場合は並列で進める
  - サブエージェントに作業を渡す場合は完全に委譲し、メインエージェントは同じ作業を重複して行わない

### Git/GitHub に関する操作

- コミットやPRは常に日本語で書いて

## ファイル作成時の注意点（ファイル作成時必ず確認）

- ファイル作成時に、そのファイルを GitHub に上げるべきではないと判断した場合は、必ず `.gitignore` に追加すること

## AGENTS.md の管理

- このファイルには、すべてのプロジェクトに共通する個人設定のみを記載する
- プロジェクト固有のパターンや規則は、各リポジトリの `AGENTS.md` に記載する
- AGENTS.md は明示的に依頼された場合のみ変更する
- 恒久化が有益と思われるルールは、必要に応じて追加を提案する

## 回答フォーマット

- 大きな論点は見出しで分け、詳細説明や手順にのみ番号付き箇条書きを使う
- 話題のまとまりごとに段落を分ける

## 既存実装の調査・調査方針

- 既存実装に関する依頼は、`一次確認` と `仕様調査` に分けて扱う

### 一次確認

- 実装の有無、定義箇所、ルーティング、参照元、入口、到達経路の確認には `explorer` を使う
- 次のいずれかに該当する場合は `spec-investigator` に切り替える
  1. 複数ファイルや複数層を横断しないと説明できない
  2. 仕様や挙動の要約が求められている
  3. 権限、状態遷移、データ構造、例外系の確認が必要
  4. 断定に追加の根拠が必要
  5. ユーザーが追加で「詳しく」「整理して」と求めた

### 仕様調査

- 仕様の把握、挙動の整理、根拠付きの説明が求められている場合は、最初から `spec-investigator` を使う
- `spec-investigator` は調査対象に応じて主となるスキルを選択して利用する
- `spec-investigator` が必要な調査を、`explorer` の一次確認やメインエージェントだけで完了しない
- 推測ではなく根拠に基づいて記述する
- 確定情報と未確認事項を明確に分ける

### 出力方針

- 調査結果は通常チャットで回答する
- 長期保存や共有を目的として、ユーザーから指定された場合のみ Markdown ファイルへ保存する
- ファイルへ保存する場合は、調査内容が識別しやすい日本語タイトルを付ける
- 根拠となるファイル・関数・コンポーネント・定義を必ず記載する
- 画面/API/状態/権限/データ構造の観点を必要に応じて横断確認する
