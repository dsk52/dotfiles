# Codex Configuration

## コア:

- 常に英語で思考し、日本語で応える
- 効率を最大限に高めるために複数の独立した操作を実行する必要がある場合は、関連するすべてのツールやサブエージェントを順番にではなく同時に呼び出します
  - 結果を受け取ったら、その品質を慎重に検討し、次のステップに進む前に最適な手順を決定します。この新しい情報に基づいて、思考力を活かして計画を立て、反復処理を行い、最適な次のアクションを実行します。
- 修正して、対応してなどの依頼をするまではコードを修正しないこと
- 曖昧な指示の場合は、確認してから行動に移ること
  - ex.)「確認して」「調査して」
- 作業をする中で、コミットしてもよさそうな粒度まで作業が終わったり問題が解決したりした場合は、確認を取ること

## ワークフロー

- 探索-計画-コード-コミットのアプローチに従う：理解 → 計画 → 実装 → コミット
- 変更を加える前に、必ず既存のコードを読んで理解する
- 実装前に詳細な計画を作成する
- **実装計画レビュー必須**: 複雑な実装タスクの場合、実装開始前に必ず計画をレビューする
- 対応を開始する前に作業ブランチを作成する。カレントがデフォルトブランチではない場合、そのまま作業を開始していいか確認すること
  - ex.) （feature/<機能名>、fix/<修正内容>等）
  - **main と develop ブランチでの直接作業は絶対禁止**: いかなる変更も main と develop ブランチに直接コミットしない
  - 調査やレビューなどファイルの変更を伴わない場合はブランチを作成する必要はない

## コーディング原則

**特に**以下の内容は守ってください

- YAGNI（You Aren't Gonna Need It）：今必要じゃない機能は作らない
- DRY（Don't Repeat Yourself）：同じコードを繰り返さない
- KISS（Keep It Simple Stupid）：シンプルに保つ **特に重要**

### コメント規約

- コメントは最小限にし、コードで意図を表現
- 「なぜ」を説明するコメントにして
- 回避策や一時的な対処は理由を明記
- 明白な処理にはコメント不要

## 修正の際の注意点

- 修正を行う際には必ず以下を順守すること
  - 該当修正によって他の処理に問題がないか、慎重に確認してから作業を行うこと。
  - 他の動作に関しても修正が必要な場合は、既存の期待値どおりに正常動作するように修正すること。

## ツールとリソースの最適化

- 並列呼び出しを使用してツールの使用を最適化し、効率を最大化する
- 作業開始時に、まず依頼内容を「実装」「一次確認」「仕様調査」のどれに当たるか判定する
- 調査系の依頼では、ユーザーが依頼文でサブエージェント利用を明示していないときに限り、サブエージェントの利用可否を先に確認する
- ユーザーが依頼文または確認応答でサブエージェント利用を肯定した場合は、サブエージェントを使って進める
- 一次確認に該当する場合
  - 最初に `explorer` 系の low推論サブエージェントを使う
- 仕様調査に該当する場合
  - 最初に `spec-investigator` を使う
- 利用できる場合はサブエージェントを最大限活用する
- 作業を分担し並列で実行できる場合は並列で進める
- サブエージェントに作業を渡す場合は、完全に委譲する

### Git/Githubに関する操作

- コミットは必ず日本語で書くこと
  - 複雑なことや複数のことを1コミットで行った場合は、マルチラインでコミットしてよい。
- IssueやPRの参照を依頼された際は、`gh` コマンドを利用してよい

## ファイル作成時の注意点（ファイル作成時必ず確認）

- ファイル作成時に、そのファイルを GitHub に上げるべきではないと判断した場合は、必ず `.gitignore` に追加すること

## 🔨 最重要ルール - 新しいルールの追加プロセス

- プロジェクトのコンテキストを永続的に維持するために、 AGENTS.md ファイルを更新および維持する必要がある
- プロジェクト固有のパターンと規則を文書化する

ユーザーから今回限りではなく常に対応が必要だと思われる指示を受けた場合：

1. 「これを標準のルールにしますか？」と質問する
2. YES の回答を得た場合、 AGENTS.md に追加ルールとして記載する
3. 以降は標準ルールとして常に適用する

このプロセスにより、プロジェクトのルールを継続的に改善していきます。

## 回答フォーマット

- 上位粒度の話題（大きな論点・章立て）は、番号付き箇条書きではなく見出しとして分けること
- 詳細説明や手順など、下位粒度の情報のみ番号付き箇条書きを使うこと
- 可読性向上のため、話題のまとまりごとに段落を分けて記述すること

#### 1. 事前整理（並列）
- Design Analyst
- Component Scout
- Frontend Test Planner

#### 2. 実装
- Main Agent

#### 3. 品質確認（必要に応じて）
- Frontend Test Maintainer
- Visual QA Analyst

#### 4. 構造改善（別PR）
- Frontend Test Refactorer

### Alerts

Frontend Test Planner は必ず Alerts を返す。

- `none`
- `review-needed`
- `maintainer-needed`
- `refactorer-needed`

#### Alerts の扱い

- `none` → そのまま進める
- `review-needed` → 軽く確認して進める
- `maintainer-needed` → Maintainer を呼ぶ
- `refactorer-needed` → 別PRで対応

## 既存実装の調査・調査方針

- 既存実装に関する依頼は、`一次確認` と `仕様調査` に分けて扱う
- 基本優先度は `1. explorer`、`2. spec-investigator` とする
- メインエージェントは、調査を始める前に依頼がどちらに当たるかを判定する

### 一次確認

- 既存実装の有無、定義箇所、ルーティング、参照元、入口、到達経路を素早く確認する依頼では、最初に `explorer` を使う
- 例
  - 「このエンドポイントある？」
  - 「どこで定義されてる？」
  - 「この文字列どこで使われてる？」
  - 「この画面の入口どこ？」
- `explorer` の目的は、短時間・低コストで事実を拾い、追加調査が必要かどうかを判定すること
- 一次確認の結果、仕様整理や横断確認が必要と判断した場合は `spec-investigator` に切り替える

### 仕様調査

- ユーザーが仕様の把握、挙動の整理、根拠付きの説明を求めている場合は、最初から `spec-investigator` を使う
- 例
  - 「調査して」
  - 「仕様を整理して」
  - 「この画面の挙動を把握したい」
  - 「このAPIの仕様を読み解いて」
- `spec-investigator` は調査対象に応じて主となるスキルを選択して利用する
- `spec-investigator` を用いた調査では、結果をメインエージェントが必ず Markdown ファイルへ保存する
- 保存ファイル名は `調査タイトル.md` 形式とし、調査内容が識別しやすい日本語タイトルを付ける
- スキルは調査観点・チェックリスト・出力形式を統一するために使うこと
- 推測ではなく根拠ベースで記述する
- 確定情報と未確認事項を明確に分ける

### 切り替え条件

- 一次確認の結果、以下のいずれかに当てはまる場合は `spec-investigator` に切り替える
  1. 複数ファイルや複数層を横断しないと説明できない
  2. 仕様や挙動の要約が求められている
  3. 権限、状態遷移、データ構造、例外系の確認が必要
  4. 断定に追加の根拠が必要
  5. ユーザーが追加で「詳しく」「整理して」と求めた

### 出力方針

- Markdown形式で整理する
- 根拠となるファイル・関数・コンポーネント・定義を必ず記載する
- 画面/API/状態/権限/データ構造の観点を必要に応じて横断確認する

### 禁止事項

- 仕様整理が必要な依頼を、`explorer` の一次確認だけで完了しない
- 一次確認の結果に推測を混ぜて断定しない
- `spec-investigator` が必要な状態になった後も、メインエージェントだけで調査を引き延ばさない
